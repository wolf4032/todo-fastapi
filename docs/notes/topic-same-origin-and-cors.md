# 同一オリジンポリシーと CORS

## オリジン

**オリジン**は「スキーム + ホスト + ポート」の組。3つすべてが一致して初めて同一オリジンになる。

| URL | `http://localhost:3000` と比べて |
|---|---|
| `http://localhost:3000/api/v1/todos` | 同一（パスは関係ない） |
| `http://localhost:8000` | 別（ポートが違う） |
| `https://localhost:3000` | 別（スキームが違う） |
| `http://127.0.0.1:3000` | 別（同じ機械を指していても、ホストの文字列が違う） |

## 同一オリジンポリシー

ブラウザは、あるオリジンのページで動く JavaScript が、**別オリジンからのレスポンスを読むこと**を原則として禁止している。

止めるのは「読むこと」であって、「送ること」ではない点に注意する。単純なリクエスト（フォーム送信相当の GET / POST）はサーバーまで届いて処理され、レスポンスもブラウザまで返ってくる。ブラウザがそれを JavaScript に渡さないだけ。

守らせているのはブラウザ自身。`curl` やサーバー同士の通信にはこのルールが無い。

### なぜあるのか

ブラウザは、リクエスト先のサイトの Cookie を自動で付けて送る。このルールが無いと、罠サイトの JavaScript が、ユーザーがログイン中の別サイト（銀行など）に `fetch` するだけで、ユーザーとして認証されたレスポンスを読めてしまう。

## CORS

**CORS（Cross-Origin Resource Sharing）**は、サーバー側が「このオリジンからなら読んでよい」とレスポンスヘッダで宣言し、同一オリジンポリシーを部分的に緩める仕組み。

```
Access-Control-Allow-Origin: http://localhost:3000
```

JSON を送る POST や、PATCH / DELETE などは、本番のリクエストの前にブラウザが `OPTIONS` で「このリクエストを送ってよいか」を問い合わせる（**プリフライト**）。許可が返らなければ、本番のリクエストは送られない。

FastAPI なら `CORSMiddleware` で設定する。許可するオリジンを環境ごとに管理する必要があり、Cookie を使う認証を足すと設定がさらに増える。

## このリポジトリの選択: 中継して同一オリジンにする

```
ブラウザ ──► localhost:3000/api/v1/todos ──► web（Next.js）──► api:8000/api/v1/todos
             （同一オリジン）                  （コンテナ間の通信。ブラウザのルールは関係ない）
```

ブラウザが話す相手は常に `localhost:3000` だけなので、CORS がそもそも発生しない。本番で前段のリバースプロキシがパスで `/api` を振り分ける構成と、ブラウザから見た URL の形が同じになる。

rewrites をやめてブラウザから直接呼ぶ案は、次の2段で失敗する。

1. `http://api:8000` は、ブラウザのいる Mac から名前解決できない（→ [topic-docker-networking.md](topic-docker-networking.md)）
2. 名前解決できる `http://localhost:8000` にしても、ページ（`:3000`）と別オリジンなので、API 側で CORS を設定しない限りレスポンスを読めない
