# Step 12: README と ADR

作成物: `README.md`、`docs/adr/`（索引 + ADR 4件）

## ADR とは

設計判断を「背景・決定・却下した案・結果」の形で1件1ファイルに残す軽量な文書。形式と運用ルールは [docs/adr/README.md](../adr/README.md) に置いた。

要点は2つ。

- **却下した案を書く**。「なぜ A か」だけでは、後から来た人が「B の方が良いのでは」と同じ検討をやり直すことになる。B を検討済みで、何が理由で落としたかが残っていれば、前提が変わったときだけ見直せばよいと分かる
- **採用済みの ADR は書き換えない**。判断を変えるときは新しい ADR を足し、古い方を「置き換え」にする。コードは常に最新の状態しか見せないが、ADR は判断の履歴を見せる

## 3つの文書の住み分け

| 文書 | 読む人 | 書くこと |
|---|---|---|
| `README.md` | このリポジトリを**使う**人 | セットアップ・コマンド・構成。「どうやるか」 |
| `docs/adr/` | 構成を**変えようとする**人 | 判断と却下した案。「なぜこうなっているか」 |
| `docs/notes/` | 学習を**振り返る**人 | 仕組みの説明とつまずき |

`docs/plan.md` の「設計判断と根拠」は計画時点の判断で、ADR はそれを実装後の事実（実測値や、やってみて分かったトレードオフ）で補ったもの。今後の参照先は ADR にする（`CLAUDE.md` の参照先も差し替えた）。

ADR の日付は、その判断が最初にコードとしてコミットされた日にした。

## 計画と実際の差（README に反映したもの）

README は計画ではなく実際のファイルに合わせて書いた。

- **`make up` / `make dev` は無い**。計画の最終検証には出てくるが、実装では通常起動を `compose.override.yaml` の `command:`（`--reload` 付き）に任せたので、`docker compose up -d` で足りる。Makefile にあるのは `debug` / `migrate` / `test` / `lint` / `format` / `prod-*`
- **`docker compose` と `make` はホストで実行する**。計画では「コンテナ内ターミナルから `make up`」と書いていたが、`devtools` には docker CLI を入れていない（→ [ADR 0001](../adr/0001-devtools-toolbox.md) の「結果」）
- **フロント追加手順の「Node の Feature を1行追加」は済んでいる**。Claude Code の導入時に `ghcr.io/devcontainers/features/node:1` を入れたため（→ [step-02-devcontainer.md](step-02-devcontainer.md)）

## 学習用コメントについて README に書いたこと

削る対象を機械的に見分ける目印（接頭辞など）は付けていない。そのため README には「記法やツールの一般的な説明は削る／このリポジトリ固有の判断理由は残す」という判断基準を書いた。`→ docs/notes/...` の参照先に説明本体があるので、コメントを削っても情報は失われない。
