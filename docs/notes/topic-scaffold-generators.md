# 設定ファイルは「標準の生成手段」があるなら使う

このリポジトリはフルスタック開発の学習が目的で、完成したファイルの中身だけでなく「実際に自分の手で作る手順」を知ることも目的の一部にしている。そのため、標準的な生成手段（CLIコマンド、または IDE のUI操作）が存在する設定・スキャフォールドファイルは、それを実際に使って作る方針にした。

## きっかけ

Step 6 で Alembic 導入時、`alembic.ini` / `migrations/env.py` / `migrations/script.py.mako` を `alembic init -t async migrations` を叩かずに手で書いてしまった。指摘を受けて一度削除し、`alembic init` を実際に実行してから中身をカスタマイズする流れに直した。

同じ観点で見直すと、他にも「標準の生成手段があったのに手で書いた／書きそうになった」ファイルがあった。

| ファイル | 標準の生成手段 | このリポジトリでの扱い |
|---|---|---|
| `backend/migrations/env.py` 等 | `alembic init -t async migrations` | 手で書いてしまい、後から生成し直した |
| `backend/pyproject.toml` の依存追加行 | `uv add <package>` / `uv add --group dev <package>` | Step 4/5 は手で書いてしまった（過去分はそのまま、Step 6以降は `uv add` に切替） |
| `.vscode/launch.json` | VS Code「実行とデバッグ」→「launch.jsonファイルを作成」→「Python Debugger: Remote Attach」 | 手で書いた。作り直してはいないが、次に同種のファイルが必要になったら使う |
| `backend/pyproject.toml` の `[project]` 雛形 | `uv init` | 手で書いた（生成物が本来の意図と食い違う部分が多く、過去分は据え置き） |

## 判断基準

生成コマンド／UI操作を優先すべきかどうかは、「その既定出力が欲しいものにほぼ近いか」で決まる。

- **近い場合（生成 → 軽微なカスタマイズ）**: `alembic init` はまさにこれ。生成された `env.py` の接続先とインポート文だけ直せば済む
- **遠い場合（生成物のほとんどを結局書き直す）**: `docker init` や VS Code の「Add Dev Container Configuration Files」は、この project の独自設計（マルチステージ Dockerfile、ツールボックス方式、compose 3層構成）とは前提が違いすぎて、生成物をほぼ全部作り直すことになる。このケースは手書きで問題ない

## 生成 → カスタマイズの差分を後から追えるようにする

「生成コマンドが作った部分」と「その後カスタマイズで足した部分」を後から見分けたいなら、**カスタマイズを始める前に一度 `git add` でステージしておく**とよい。

```bash
git add backend/migrations/env.py
```

Gitの差分は「以前に記録した状態」と「今の状態」の比較でしかないため、生成直後の状態を一度も記録していないと、後から正確な差分としては復元できない。ステージを挟んでおけば、その後の編集は `git diff`（未ステージ差分）でカスタマイズ箇所だけを正確に確認できる。今回はこの手順を踏まずに直接編集してしまったため、`env.py` については日本語コメント（`→ docs/notes/...` 付き）が代わりの目印になっている。

## 他のプロジェクトに応用するときの心構え

新しい設定ファイルを書き始める前に、一度「これ、標準の生成コマンドや IDE のUI操作は無いか？」と疑う。無ければ手で書けばよいし、あれば先にそれを実行してから中身を読み、必要な差分だけ直す。
