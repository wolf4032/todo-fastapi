# 静的解析と pre-commit の仕組み

Step 10 で導入した3つの道具（ruff / mypy / pre-commit）が、それぞれ**何を見ていて、いつ動くのか**。

## 3つの道具の守備範囲

「静的解析」は**プログラムを実行せずにソースコードを読んで問題を見つける**手法の総称。実行して確かめるテストとは別の層で、テストが書かれていない箇所にも一律に効くのが利点。

| 道具 | 見るもの | 直すか |
|---|---|---|
| **リンタ** (ruff check) | 規約違反・怪しい書き方（未使用 import、変数の書き忘れ、罠になる書き方） | 報告。一部は `--fix` で自動修正 |
| **フォーマッタ** (ruff format) | 見た目だけ（改行位置、クォート、インデント） | 常に書き換える |
| **型チェッカ** (mypy) | 型ヒントどうしの整合性 | 報告のみ |

### リンタとフォーマッタの境目

判定基準は「**構文木（AST）が変わるか**」。フォーマッタは空白・改行・クォートしか触らないので、パースした結果の木構造は前後で一致する。リンタの修正は木構造そのものを書き換える。

言い換えると、**フォーマッタの変更は挙動を絶対に変えない**が、**リンタの修正は挙動が変わりうる**。だから ruff の自動修正には「安全（`--fix`）」と「安全でない（`--unsafe-fixes`）」の区別がある。

**リンタが直すもの**（意味に踏み込む）

```python
# before                         # after
if x == None:                    if x is None:          # E711
import os, sys                   # 使っていない import は削除    # F401
from typing import Optional      # (削除)                # UP035
def f(x: Optional[int]):         def f(x: int | None):  # UP007
for i in range(len(items)):      for i, item in enumerate(items):   # B007 等
if a: return True
else: return False               return bool(a)         # SIM103
```

`x == None` と `x is None` は、`__eq__` を定義したクラスでは**結果が違いうる**。それでもリンタが直すのは「ほぼ確実に後者が意図だから」であって、意味が同じだからではない。

**フォーマッタが直すもの**（見た目だけ）

```python
# before
x = { 'a':1,'b':2 }
def f(a,b):
    return a+b
result = some_function(argument_one, argument_two, argument_three, argument_four_long)

# after
x = {"a": 1, "b": 2}


def f(a, b):
    return a + b


result = some_function(
    argument_one, argument_two, argument_three, argument_four_long
)
```

クォートの統一、空白の入れ方、関数間の空行2つ、長い行の折り返し。どれも実行結果は1ビットも変わらない。

| | リンタ (`ruff check`) | フォーマッタ (`ruff format`) |
|---|---|---|
| 触るもの | 構文木 | 空白・改行・クォートのみ |
| 挙動 | 変わりうる | 絶対に変わらない |
| 設定 | どのルールを有効にするか選ぶ | ほぼ選べない（line-length 程度） |
| 人の判断 | 要ることがある（`# noqa`） | 基本不要 |

フォーマッタに設定項目がほとんど無いのは意図的で、「整形の流儀でレビューが揉めないようにする」ことが目的だから。

### 守備範囲は排他ではなく、重なる

「リンタはフォーマッタが触らないものを見る」と整理したくなるが、正確ではない。**両者の範囲は重なっている**。

Step 10 で実際に見た例。`migrations/versions/` の docstring にあった行末空白は、

- **リンタ**が `W291 Trailing whitespace` として**報告**し、
- **フォーマッタ**が docstring の正規化として**修正**した。

同じ1つの問題に両方が手を伸ばしている。

重なった領域は**競合の種**になる。リンタが「こう直せ」と言い、フォーマッタが別の形に戻す、という往復が起きうるため。そこで実務では「**重なる部分はフォーマッタに任せ、リンタ側のルールを無効にする**」という調整をする。

この構成で `E501`（行が長すぎる）を `ignore` に入れたのがまさにそれ。ruff 自身も同じ発想で、pycodestyle の空白・インデント系ルール（`E1xx` / `E2xx` / `E3xx` など）の多くを既定では有効にしていない。

立ち位置としてはこう整理するのが正確。

- **フォーマッタ** … 「見た目を1つに決める」＝**選択肢を消す**。だから設定がほぼ無い
- **リンタ** … 「書き方の良し悪しを指摘する」＝**ルールを選ぶ**。だから設定が長くなる
- **重なった領域** … フォーマッタを優先し、リンタ側を外す

### ruff

Rust 製で、従来別々だったツール（flake8・isort・pyupgrade・black など）の機能を1つのバイナリに集約したもの。ルールは**元ツールに由来する接頭辞**（`E`=pycodestyle、`F`=Pyflakes、`I`=isort、`UP`=pyupgrade、`B`=bugbear …）で選ぶ。

### mypy

型ヒント（`def f(x: int) -> str:` の `int` や `str`）は Python の実行時には**一切チェックされない**。ただの注釈で、嘘を書いても動く。mypy はそれを実行前に突き合わせる。

`strict = true` は個別オプション（型ヒントの無い関数を禁止、`Any` の混入検出など）をまとめて有効にするスイッチ。

型チェッカが表現しきれない箇所は、**その行だけ** `# type: ignore[エラーコード]` で逃がす。コード名を省くと全種類のエラーを黙らせてしまうので必ず付ける。なお `# type: ignore` を**行頭のコメントとして単独で書くと**、mypy は別の意味（型コメント）に解釈して構文エラーになる。必ず対象の行末に置く。

## pre-commit の仕組み

`git commit` を実行したとき、コミットが確定する前に**検査を自動で走らせる**道具。

### git hook そのもの

git には元々、特定のタイミングで `.git/hooks/` 配下のスクリプトを実行する仕組みがある（`pre-commit`、`commit-msg`、`pre-push` など）。`.git/` は**クローンしても共有されない**ため、素の git hook はチーム全員に配る手段が無い。

pre-commit（ツール名）は、この配布問題を「検査の定義は `.pre-commit-config.yaml` としてリポジトリに入れ、`.git/hooks/pre-commit` はそれを呼ぶだけの短いスクリプトにする」で解決する。その短いスクリプトを書き込むのが `pre-commit install` で、**クローンごとに1回必要**。

### 検査ツールはどこから来るか

`.pre-commit-config.yaml` の `repo` + `rev` を見て、pre-commit が**hook ごとに隔離環境を作り、そこにツールを入れる**（置き場は `~/.cache/pre-commit`）。

つまり ruff をどこにもインストールしていなくても hook は動く。代わりに、**同じツールのバージョン指定がプロジェクト内に2箇所できる**（`rev` と依存ファイル）。ずれると「エディタと `make lint` は通るのに commit で弾かれる」が起きるので、更新時は両方を揃える。

### 対象は「ステージ済みの変更」だけ

hook が走る前に、pre-commit は**未ステージの変更を一時退避（stash）する**。手元で書きかけの部分が検査に混ざらないようにするため。検査後に戻される。

自動修正する hook（`ruff-check --fix` など）がファイルを書き換えた場合、pre-commit は**その回のコミットを失敗させる**。書き換えた内容を人間が確認してから `git add` し直させるためで、正常な動作。同じ `git commit` をもう一度打てば今度は通る。

### 手で走らせる

```
pre-commit run --all-files
```

導入直後や、hook を足したときの一括適用に使う。commit 時は変更されたファイルだけが対象なので、既存コード全体には当たらない。

急ぎで飛ばしたいときは `git commit --no-verify`。ただし CI でも同じ検査を回しておかないと、飛ばしたまま main に入る。
