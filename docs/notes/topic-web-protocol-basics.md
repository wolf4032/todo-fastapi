# Webの通信まわりの地図（ソケット・HTTP・WSGI/ASGI・httpx）

Step 9 でテストに `httpx` と `ASGITransport` が出てきた際、そもそも「HTTPリクエストが届いてFastAPIの関数が呼ばれるまで」に何が挟まっているのかを整理したもの。

## 4つの層

下から順に積み上がっている。

| 層 | 正体 | 今回の担当 |
|---|---|---|
| 1. ソケット | OS が提供する「通信の口」。2台のマシンの間にバイト列を流す管を1本通す。中身が何かは関知しない | OS |
| 2. HTTP | その管に流す**文字列の書式の取り決め**。実体はただのテキスト | 規格 |
| 3. HTTPサーバー | ソケットで待ち受け、届いたテキストを解析して Python のデータ構造に変換する | uvicorn |
| 4. ASGI | 変換済みのデータをアプリへ渡すときの**形式の取り決め** | 規格 |
| （その上） | ルーティング・バリデーション・業務ロジック | FastAPI + `app/` |

2 の「HTTP は実体としてただのテキスト」が一番イメージしづらいが、ブラウザや `curl` が送っているのはこういう文字列にすぎない。

```
GET /health HTTP/1.1
Host: localhost:8000
Accept: application/json
```

郵便に例えるなら、**ソケットが郵便網、HTTP が封筒と便箋の書き方、uvicorn が郵便局、ASGI が郵便局から社内へ渡すときの受け渡し書式**にあたる。

このプロジェクトで 1〜3 を自分で書くことはない。深く知る必要が出るのは、自分で HTTP サーバーを実装するときか、通信性能の問題を追うときだけ。

## WSGI と ASGI

どちらも「Python の Web アプリと、それを動かすサーバーの間の**呼び出し方の取り決め**」。「この形の関数さえ用意すれば、どのサーバーからでも呼べる」という規格。

| | 正式名称 | 同期/非同期 | 代表例 |
|---|---|---|---|
| WSGI | Web Server Gateway Interface | 同期専用 | Flask、Django（同期部分）、gunicorn |
| ASGI | **A**synchronous Server Gateway Interface | 非同期 | FastAPI、Starlette、uvicorn |

先に WSGI があったが、規格が「同期関数」と定めてしまっているため、WebSocket や `async`/`await` を後付けで表現できない。そこで**拡張ではなく別規格**として ASGI が作られた、というのが経緯。

**WSGI を先に理解する必要はない。** 役に立つのは「なぜ ASGI がこの形なのか」の背景としてだけで、本プロジェクトで WSGI のコードを書くことも読むこともない。

### ASGI は非同期一本だが、同期のコードも書ける

規格そのものは非同期一本で、アプリは `async def` の呼び出し可能オブジェクトでなければならない。**サーバーとアプリの境界面は常に非同期**。

一方でアプリを書く側から見ると、エンドポイントを `def`（同期）で書くこともできる。これは ASGI の規格が同期を許しているのではなく、**FastAPI が「これは同期関数だ」と判別して別スレッドへ逃がしてくれている**ため。この挙動と、`async def` の中に同期の重い処理を書いたときの危険性は [topic-async-await.md](topic-async-await.md) を参照。

## httpx

**プログラムから HTTP リクエストを送るためのライブラリ。** ブラウザや `curl` がやっていることを Python コードからやる道具。

Python では長らく `requests` が定番だったが、`requests` は同期専用。httpx は書き味を `requests` に寄せたまま、次を備える。

- 同期（`httpx.Client`）と非同期（`httpx.AsyncClient`）の両方
- HTTP/2 対応（`requests` は HTTP/1.1 のみ）

厳密には 100% の互換ではないが、「requests に非同期対応を足した現代版」という捉え方で実用上は困らない。

## ASGITransport

httpx は「リクエストを組み立てる部分」と「実際に送り出す部分（**Transport**）」が分離された設計になっていて、この Transport を差し替えられる。

| Transport | 何をするか |
|---|---|
| 通常（既定） | 組み立てたリクエストをソケットに流す（上の地図の 1→2→3 を通る） |
| `ASGITransport` | ソケットを使わず、**アプリを ASGI の形式で直接呼び出し**、返ってきたものをレスポンスオブジェクトに戻す |

つまり地図の 1〜3 を丸ごと飛ばして 4 に直結させる部品。

### 「エンドポイント関数を直接呼ぶ」のとは違う

呼ばれるのはエンドポイントの関数ではなく、**`app` オブジェクト（FastAPI アプリ本体）**である。この違いが重要。

```python
# これはエンドポイント関数を直接呼んでいる。戻り値しか検証できない
todo = await create_todo(TodoCreate(title="牛乳を買う"), db)

# これは app 全体を呼んでいる。HTTP としてのふるまいを検証できる
res = await client.post("/api/v1/todos", json={"title": "牛乳を買う"})
assert res.status_code == 201
```

前者では、ステータスコードが 201 なのか、`title` が空文字なら 422 になるのか、存在しない ID で 404 に変換されるのかを**一切検証できない**。

`ASGITransport` はアプリ全体を呼ぶので、その内側にある次のものは**本番とまったく同じように動く**。

- ルーティング（`GET /api/v1/todos/5` → `read_todo` 関数の対応付け）
- ミドルウェア（リクエストID付与・構造化ログ）
- `Depends` の解決（ここに `dependency_overrides` が効く → [topic-fastapi-dependency-injection.md](topic-fastapi-dependency-injection.md)）
- Pydantic のバリデーションと `response_model` による整形
- 例外ハンドラ（`HTTPException` → 統一エラー形式の JSON）

飛ばされるのはソケット通信と HTTP テキストの組み立て・解析だけ。「本来の形式の通信ではない」が、検証したい部分はほぼ全部通っている。

### 何が嬉しいか

- **速い**（ネットワークを介さない）
- **サーバーを起動しなくていい**。uvicorn が動いていなくてもテストできるし、ポートの競合も起きない
- **ネットワーク由来の不安定さがない**。タイミングによって稀に失敗する、いわゆる flaky なテストになりにくい
- CI で「アプリを起動 → 起動完了を待つ → テスト → 落とす」という手順が不要になる
