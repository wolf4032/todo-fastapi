# バージョン選定の考え方: 言語本体とライブラリでは基準が違う

## Python本体: 「最新」と「枯れるまで待つ」は矛盾しない

新規プロジェクトで最新の安定版を選ぶのは基本的に妥当。理由は「まだ何も古いバージョンのAPIに依存したコードが存在しない」ため、既存プロジェクトの依存アップグレードのような移行コストが発生しない。

ただしPython本体の選定には、通常のライブラリには無い注意点がある。**新しいマイナーバージョンがリリースされた直後は、C拡張を含むライブラリ（`asyncpg`、`pydantic-core`など）のビルド済みwheelがまだ揃っていないことがある。** この場合 `pip install` がソースからのビルドにフォールバックして失敗したり遅くなったりする。

これは「最新を避けるべき」という話ではなく、「**リリース直後の最新**」と「**エコシステムが追いついた後の最新**」を区別すべき、という話。実際にPython 3.14（2025年10月リリース）について2026年8月時点で調べたところ、`asyncpg`（2025年11月にwheel公開）、`SQLAlchemy`（2.0.52で正式サポート）、Docker公式の `python:3.14-slim` イメージ、いずれも既に対応済みだった。つまり技術的な「動くか」の閾値は、リリースから数ヶ月で越えられる。

## もう1つの軸: ネット上の周辺知識（troubleshooting情報）の蓄積量

技術的に動くかどうかとは別に、**ブログ記事・Qiita・Stack Overflow・GitHub Issueの解決報告などの蓄積量**という軸がある。これは「越えたか越えていないか」の閾値ではなく、時間とともに継続的に積み上がっていくもの。動くようになった直後と、動くようになってから1年経った後とでは、後者の方が圧倒的に厚みがある。

この蓄積量は、学習目的のプロジェクトでは特に効く。経験を積んだ人であれば公式ドキュメントやソースコードを直接読んで自己解決できるが、初出の概念を一つずつ学びながら進めている場合、「同じエラーで他の誰かがつまずいて解決した記事」が見つかるかどうかの差は大きい。

**結論**: 「wheelがあるかどうか」のような技術的な閾値は短期間で埋まるが、周辺知識の蓄積量の差はそう簡単には埋まらない。技術的に動くことが確認できても、周辺知識の厚みも判断材料に加えると、あえて1世代前の枯れたバージョンに留める選択は十分合理的（本リポジトリはこの理由でPython 3.13を維持することにした）。

## ライブラリ個別のバージョンには、この基準をそのまま持ち込まない

「情報の蓄積量が多いバージョンを選ぶ」という考え方は、Python本体の選定ほどには個別ライブラリの追加（`uv add <package>`）には当てはまらない。理由は3つ。

1. **`uv.lock` が再現性の問題を既に解決している**: Python本体の選定が重かったのは「開発・CI・本番で環境が食い違うと困る」という再現性の話も絡んでいたが、ライブラリ個別のバージョンは `uv.lock` が全環境で厳密に固定するので、その心配は無い
2. **ライブラリの困りごとは公式ドキュメント/Changelog/GitHub Issueで解決するのが基本**: 成熟した公式ドキュメントが充実したライブラリ（Alembic、SQLAlchemyなど）では特にそう。ブログ記事の量に頼る場面は言語本体ほど多くない
3. **意図的に古いバージョンを選ぶと、実際のバグ修正やセキュリティ修正を素通りする**: それを「検索のしやすさ」のために手放す価値は、大抵の場合無い

なので個別ライブラリは `uv add` にバージョン指定を任せ、常に解決できる最新を使うのが `uv` の思想（＝バージョン選定の悩みは resolver と lockfile に任せる）にも沿う。具体的な既知の重大バグのような理由が出てきたら、その時に個別対応すればよい。
